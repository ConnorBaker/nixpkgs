# CUDA driver selection

On `feat/cuda-compat-driver-shim`, a packaged CUDA consumer selects a real `libcuda.so.1` at its first lookup. NVIDIA’s `cuda_compat` backports user-space driver components, including the PTX and NVVM compilers, to supported older kernel drivers. The running kernel driver comes from the host, including inside a container. The user can build once and run on different hosts. The application controls CUDA initialization and device visibility. [NVIDIA forward compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/latest/forward-compatibility.html)

## Which driver loads

An existing binding to the SONAME wins in its loader namespace. For a new binding, an upgrade requires an openable `/dev/nvidiactl` character device, a readable kernel release, a strictly newer candidate, and a matching kernel branch in NVIDIA’s format-1 ELF note. Missing evidence leaves the usual driver search in effect. The comparison uses the kernel release. An eligible candidate can therefore precede a newer, still-unloaded library on `LD_LIBRARY_PATH`. Explicit paths remain under the caller’s control and can load another provider. NVIDIA’s branch test cannot guarantee hardware eligibility or graphics interoperability. [NVIDIA’s container policy](https://github.com/NVIDIA/nvidia-container-toolkit/blob/v1.20.2/cmd/nvidia-cdi-hook/cudacompat/cuda-elf-header.go)

| First lookup | Source of candidates |
| --- | --- |
| A CUDA redistributable calls `dlopen` in a stock process | The toolkit that supplied that library |
| A participating executable or one of its plugins requests the driver, including through `DT_NEEDED` | The newest eligible candidate registered by a participating output in that loader namespace |
| An unmodified stock process first loads a plugin directly linked to `libcuda.so.1` | The process’s ordinary loader search |
| An unmodified library makes the first request in a stock process | The requesting library’s ordinary loader search |

For example, with both 13.3 and 13.5 runtimes mapped on kernel 615, the first call through 13.3 used host 615 and the first call through 13.5 used `cuda_compat` 620. With the auditor active, either caller used 620. Importing the runtimes in either order left the decision open. Each subsequent bare-name lookup reused the bound library.

## How the package set implements it

- **Toolkit libraries.** Each supported `cuda_compat` output installs a manifest and a private helper. A redistributable’s glibc `dlopen` import binds to a symbol unique to that toolkit. For an eligible driver lookup the helper calls glibc with the SONAME and a private `DT_RPATH` containing only the chosen driver link. This lets glibc reuse an existing binding under its loader lock. Pass-through tail calls preserve the original namespace, RUNPATH and `$ORIGIN`. Static CUDART carries a small Rust object that temporarily opens the same helper when needed. The final executable or plugin can use it without acquiring a shared CUDART dependency.
- **Companions.** The compatibility driver opens an archived companion by its absolute path even if an older compiler with the same SONAME is already loaded. The installer embeds the archive’s aliases and canonical paths as NUL-terminated data. Other names follow ordinary lookup. Video, display and OptiX components come from the host. [Archive contents](https://docs.nvidia.com/deploy/cuda-compatibility/latest/forward-compatibility.html#installing-the-cuda-forward-compatibility-package)
- **Participating executables.** The propagated hook appends the auditor to the final ELF’s effective `DT_AUDIT` list, preserving existing auditors. Intermediate DSOs do not reliably propagate audit metadata. Each participating output records its manifests in `nix-support/cuda-driver-selection`. The auditor verifies mapped device and inode through `/proc/self/maps`, registers that output on open, and withdraws it when its last object in that namespace closes. It retains paths previously returned to glibc because another auditor can still hold their addresses. Overlapping callbacks or a fork inheriting a busy registry disable further audit substitutions. The independent toolkit helper remains usable. [glibc audit callbacks](https://snapshots.sourceware.org/glibc/trunk/latest/manual/html_node/Audit-API-Callbacks.html)
- **Host discovery.** After Nix glibc exhausts its ordinary search, the auditor can search host driver directories on NixOS, distributions and container images. A host compiler receives this fallback only for a verified host driver or companion. CUDA Tile, Numba and numba-cuda previously hard-coded driver paths. They now call the toolkit helper on first use. The cuda-bindings extension intercepts its own calls at link time. These packages have a final host-directory retry using a small ELF dependency with inherited RPATH, which also lets the host driver locate its JIT libraries. In that retry a host compiler can precede an unbound compiler on `LD_LIBRARY_PATH`.
- **Packaging.** `buildInputs = [ cudaPackages.cuda_cudart ];` brings the consumer hook through the development output. An explicit `cuda_cudart.out` retains the SDK layout and bypasses executable tagging. Compiler and ELF editing tools are build-time dependencies. GPU checks running before fixup append the available NixOS driver directory to the exported library search path.

The auditor and the helper share a `no_std` Rust policy archive. The auditor exports four eagerly bound glibc callbacks and uses the invoking loader’s libc. Rustix handles file descriptors and fallible reads. glibc supplies the startup auxiliary vector. Rust’s explicit `become` tail calls preserve the return address glibc uses to identify a `dlopen` caller, even without optimization. The cuda-bindings adapter also checks that address before applying its extension-specific retry. The pinned Rust compilers require crate-scoped unstable features for those operations. [glibc dlopen](https://codebrowser.dev/glibc/glibc/dlfcn/dlopen.c.html) · [Rust explicit tail calls](https://doc.rust-lang.org/unstable-book/language-features/explicit-tail-calls.html)

## Boundaries and evidence

A stock host resolves a plugin’s eager relocations and imported data before any plugin constructor runs. Adding CUDART to that plugin’s dependencies or installing a public forwarding stub cannot interpose this decision transparently. A participating plugin manager can open the chosen real driver before opening a known plugin. The original public shim also missed newer driver exports and initialized device visibility too early. [glibc dependency loading](https://codebrowser.dev/glibc/glibc/elf/dl-open.c.html) · [Original forwarding prototype](https://github.com/ConnorBaker/nixpkgs/tree/52acfcbd12cb3184257cf6cd16aa4fbfaa499e63/pkgs/development/cuda-modules/prototypes/cuda-compat-shim)

The auditor requires glibc audit ABI 2 and declines secure execution. On Ubuntu 20.04 AArch64 an ABI 1 auditor crashed during `dlmopen` even with no-op callbacks. The per-library helper worked with glibc 2.31. Fully static glibc executables encountered CUDA error 304 with both versions of the CUDART archive. [glibc audit ABI change](https://sourceware.org/pipermail/libc-stable/2022-April/001467.html)

Legacy Tegra and dedicated Orin configurations keep host lookup. Visible nvgpu devices or modules also suppress the SBSA upgrade on generic AArch64 and can affect a mixed IGX host. Orin upgrades require the appropriate JetPack compatibility library, which an operator can explicitly put first on the application’s library search path. The former `enableCudaDriverCompat` option has no effect. WSL uses its Windows-provided driver. Mounted WSL and Jetson layouts have been exercised. Hardware execution on both remains unverified. [JetPack upgrade matrix](https://docs.nvidia.com/cuda/cuda-for-tegra-appnote/index.html#cuda-upgrade-package-supported-jetpack-versions) · [CUDA on WSL](https://docs.nvidia.com/cuda/wsl-user-guide/)

Run `nix-build -A cudaPackages_13_5.tests.driver-selection` for the real-loader fixtures. They cover direct linkage, shared and static CUDART, first binding, namespaces, multiple toolkits, chained auditors and lazy Python requests. Native and cross-built fixtures ran on AArch64, and native x86-64 fixtures ran through Tribuchet. Hardware runs on Ubuntu GB10, NixOS RTX 4090 and an NVIDIA CDI container returned zero SAXPY error, cuBLAS sum 9, and JIT kernel result 42. An occasional GB10 context allocation returned error 2 and passed in fresh processes. Its cause remains open. The earlier experiment log records the individual controls, including PTX error 222 with a mismatched compiler.
